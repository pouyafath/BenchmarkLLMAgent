\begin{abstract}
GitHub issues serve as the primary communication channel between users and developers for reporting bugs, requesting features, and proposing refactoring tasks. Issue descriptions are frequently vague, incomplete, or lacking essential technical details, which hinders both human developers and automated issue-solving agents. Large Language Model (LLM)-based agents offer the potential to automatically \emph{enhance} issue descriptions by adding context, clarifying ambiguities, and structuring information. If agents solve issues from text, better text should mean better fixes. We test this assumption directly and at scale. We construct a SWE-bench-Live--style benchmark of 3,285 issue instances from 613 popular Python repositories and, from it, a validated execution subset of \textbf{382 issues}, each with a buildable Docker environment and a gold patch. On this subset we run a full \textbf{enhancer $\times$ solver matrix}: coding agents used as \emph{enhancers} (OpenHands, SWE-agent, Aider), a reward-gated selective enhancer (\ourmethod{}), and a no-enhancement baseline, against the same agents used as \emph{solvers} --- all driven by a single open-weight model (Qwen3-32B) to isolate the enhancement variable. We evaluate not ``did the patch change'' but ``does the patch \textbf{pass the repository's tests}'', using a gold-patch-gated, multi-method evaluability protocol that yields \textbf{279 of 382 issues (73.0\%)} as trustworthy to evaluate. Our results show that: (1) across the controlled agentic enhancer $\times$ solver matrix, issue enhancement produces \textbf{no statistically significant improvement in fix correctness} (paired McNemar exact test, all $p \ge 0.489$), and a zero-shot prompt enhancer likewise never helps and tends to hurt; the one promising small-sample signal weakened rather than strengthened as the sample grew, the signature of a non-effect; solver choice, not the wording of the report, dominates outcome (Aider 44\% $\gg$ OpenHands 22\% $\gg$ SWE-agent 6\%). (2) No feature --- across an 81-feature SE representation plus 500 TF-IDF terms --- predicts a better enhancement under either an intrinsic (reward-model) or a downstream definition of success (all models at chance, ROC-AUC $\approx 0.49$--$0.56$); strikingly, enhancement \emph{does} raise the intrinsic quality score (57\% of reports improve) yet yields no downstream correctness gain, so \textbf{text-quality improvements do not transfer to program repair}. (3) A qualitative analysis characterizes how the agents rewrite --- a uniform Problem/Reproduction/Expected template that lifts the quality score but, being often unfounded, does not help the solver. We release the benchmark, the evaluation pipeline, and all experimental artifacts.
\end{abstract}

\section{Introduction}
\label{sec:introduction}
%==============================================================================

GitHub issues are the primary mechanism through which developers and users communicate about software defects, feature requests, and maintenance tasks~\cite{zhang2025swebenchlive, jimenez2024swebench}. A well-written issue report contains a clear problem description, reproduction steps, expected versus actual behavior, and relevant technical context such as version information, stack traces, or code snippets. When these elements are present, both human developers and automated solving agents can effectively diagnose and resolve the underlying problem.

In practice, however, issue descriptions are frequently incomplete, vague, or poorly structured. Prior work on bug report quality has shown that missing reproduction steps, ambiguous descriptions, and insufficient context are among the most common reasons for delayed or failed issue resolution~\cite{bettenburg2008what, zimmermann2010what}. This quality gap is particularly consequential for automated issue-solving systems, which rely on the issue description as their sole input for generating code patches~\cite{jimenez2024swebench, yang2024swe}.

The emergence of LLM-based coding agents---such as OpenHands~\cite{wang2024openhands}, SWE-agent~\cite{yang2024swe}, Aider~\cite{aider2024}, and AutoCodeRover~\cite{zhang2024autocoderover}---has opened a new possibility: using these agents not only to \emph{solve} issues but also to \emph{enhance} issue descriptions before solving. An enhancement agent can analyze the codebase, identify relevant source files, extract failing test information, and restructure the issue description to provide a clearer specification. If effective, this pre-processing step could improve the success rate of downstream solving agents. This hypothesis motivates a growing line of issue-enhancement tools, including reward-gated report rewriting. Yet enhancement is almost always evaluated \emph{intrinsically}---does the rewritten report score higher on a text-quality metric---and rarely \emph{extrinsically}: does a better report actually cause a better downstream fix.

This paper closes that gap. Existing benchmarks such as SWE-bench~\cite{jimenez2024swebench} and SWE-bench-Live~\cite{zhang2025swebenchlive} focus exclusively on issue \emph{solving}, treating the issue description as a fixed input. We instead treat the issue text as a \emph{manipulable} stage. Our approach is built on the \emph{solving-as-evaluation} paradigm: we measure the quality of an enhancement not through subjective text ratings but through its downstream effect on solver performance. Formally, for an enhancement agent $E$ and a solver agent $S$, the enhancement value is:
\begin{equation}
\Delta_{\text{resolved}} = \text{Resolved}(S, E(\text{issue})) - \text{Resolved}(S, \text{issue})
\label{eq:enhancement_value}
\end{equation}

\noindent where a positive $\Delta_{\text{resolved}}$ indicates that enhancement improved solving performance. This indirect evaluation provides an objective, reproducible measure of enhancement quality that is grounded in functional correctness.

Our study analyzes GitHub issue enhancement along three research questions, each with its own method:

\textbf{RQ1: What is the ability of generative AI in enhancing GitHub issue reports?} We benchmark an enhancer--solver agentic workflow: each enhancer rewrites the report, each solver then attempts a patch, and we measure enhancement ability by whether the resulting patch passes the repository's tests. We evaluate a no-enhancement baseline plus enhancers of increasing sophistication across three solver agents, holding the model fixed.

\textbf{RQ2: What features are related to a better enhancement?} We fit a logistic regression over textual, structural, and enhancement-derived features to identify which are associated with a successful enhancement outcome, under both an intrinsic (reward-model) and an extrinsic (downstream-fix) definition of success.

\textbf{RQ3: How are GitHub issue reports enhanced by generative-AI agents?} We perform a qualitative analysis of the agent-generated reports to characterize recurring enhancement patterns and the failure modes that explain the RQ1 result.

The main contributions of this paper are as follows:
\begin{enumerate}
\item We construct a large-scale dataset of 3,285 GitHub issue instances from 613 repositories, and a validated execution subset of 382 instances each with a buildable environment and gold patch, suitable for the extrinsic evaluation of issue enhancement.
\item We propose and apply the \emph{solving-as-evaluation} framework, measuring enhancement quality through downstream solver performance under a controlled model rather than subjective text assessment.
\item We provide a large-scale extrinsic benchmark (RQ1) whose finding is a \textbf{rigorous negative result}: no enhancement condition reliably improves fix correctness at any tested scale, and the one small-sample signal is traced to sampling noise by replication.
\item We provide a feature-level (RQ2) and qualitative (RQ3) account of which report/enhancement properties and rewrite behaviors relate to enhancement outcomes, surfacing an intrinsic-improves / extrinsic-flat gap.
\item We contribute an evaluation methodology---a gold-patch-gated, three-method evaluability gate (73.0\% coverage, 279/382) with an artifact-recovery discipline---that we argue is a prerequisite for trustworthy agent-repair measurement.
\item We release the benchmark dataset, evaluation pipeline, and all experimental artifacts in our replication package~\cite{replication2026}.
\end{enumerate}

The rest of the paper is organized as follows: Section~\ref{sec:background} discusses background and related work. Section~\ref{sec:methodology} presents our methodology. Section~\ref{sec:results} presents the results for each research question. Section~\ref{sec:discussion} discusses implications. Section~\ref{sec:threats} discusses threats to validity. Section~\ref{sec:conclusion} concludes.

\section{Background and Related Work}
\label{sec:background}
%==============================================================================

\subsection{Issue Report Quality}

The quality of bug reports and issue descriptions has been extensively studied. Bettenburg et al.~\cite{bettenburg2008what} surveyed developers and found that steps to reproduce, stack traces, and test cases are the most valuable elements in bug reports, yet they are frequently missing. Zimmermann et al.~\cite{zimmermann2010what} identified that incomplete information is the primary barrier to bug fixing, with a large fraction of reports lacking sufficient detail.

Several approaches have been proposed to improve bug report quality. Duplicate detection systems~\cite{sun2011towards, lazar2014generating} help reduce redundant reports. Automated triaging~\cite{anvik2006should, murphy2004automatic} routes reports to appropriate developers. More recently, approaches that automatically augment bug reports with relevant source code~\cite{wong2014autolocate, moreno2015arena} have shown promise. All of this measures quality \emph{intrinsically} (a text or model score). To our knowledge no prior study measures whether such rewriting propagates to downstream \emph{repair correctness}, which is the gap we close. Our work also differs by leveraging LLM-based agents as enhancement tools rather than rule-based or retrieval-based augmentation.

\subsection{SWE-bench and Issue-Solving Benchmarks}

SWE-bench~\cite{jimenez2024swebench} introduced a benchmark of software engineering problems drawn from real GitHub issues. Given a codebase and an issue description, a model generates a patch evaluated against unit tests. The benchmark uses two test categories: \emph{fail-to-pass} (F2P) tests that should change from failing to passing after the patch, and \emph{pass-to-pass} (P2P) tests that must continue passing to ensure no regressions. SWE-bench-Live~\cite{zhang2025swebenchlive} extended this paradigm with an automatically updatable benchmark spanning many repositories and tasks derived from recent issues, addressing staleness and limited coverage. These systems are evaluated on the \emph{fix}; the issue text is taken as fixed input. We reuse the solving step as an evaluation instrument and ask whether \emph{improving} the issue text changes the fix---an extrinsic question these benchmarks do not pose.

\subsection{LLM-Based Coding Agents}

LLM-based coding agents form a diverse ecosystem of tools capable of interacting with codebases, executing commands, and generating patches. SWE-agent~\cite{yang2024swe} introduces an agent-computer interface designed for software engineering tasks. OpenHands~\cite{wang2024openhands} provides a platform for AI-powered software development agents. Aider~\cite{aider2024} is a command-line tool for AI-assisted pair programming. AutoCodeRover~\cite{zhang2024autocoderover} performs autonomous program improvement through structured code search. While designed for solving, their ability to understand code context, identify relevant files, and generate structured analysis makes them natural candidates for issue enhancement---a use case we systematically evaluate.

\subsection{Issue Enhancement}

Issue enhancement refers to automatically improving an issue description by adding relevant context, clarifying ambiguities, restructuring content, or appending diagnostic information. Unlike issue solving, which produces a code patch, enhancement produces an improved textual description that can be consumed by either human developers or automated solvers. To the best of our knowledge, no prior work has systematically benchmarked issue enhancement agents or measured the downstream solving impact of enhancement. Our work fills this gap by providing both a benchmark and a comprehensive extrinsic evaluation.

\subsection{Data Collection and Dataset Construction}

We construct a SWE-bench-style benchmark from recent GitHub issues to ensure evaluation data postdates the training cutoffs of the LLMs under study. Fig.~\ref{fig:data_collection} illustrates the pipeline.

\subsubsection{Stage 1: Repository Selection}
We fetch GitHub repositories with more than 1,000 stars, yielding 10,609 repositories, and apply three quality filters: \textbf{(i) language}---Python constitutes more than 60\% of the codebase; \textbf{(ii) fork activity}---more than 200 forks; and \textbf{(iii) issue and PR volume}---the combined count exceeds 200. After these filters, 3,621 repositories with 10,463 associated issues remain.

\subsubsection{Stage 2: Temporal Filtering}
To ensure recency and avoid training-data contamination, only issues created after August 1, 2025 are retained. This reduces the dataset to 2,748 repositories with 7,714 issues.

\subsubsection{Stage 3: Merge-Based Linking and Test Coverage}
We retain only issues that (a) were closed by a \emph{merged} pull request (establishing a ground-truth fix); (b) whose PR includes a non-empty code patch and a non-empty test patch; and (c) that have at least one pass-to-pass test ($\text{P2P} > 0$). This yields 613 repositories with 3,285 issues.

\subsubsection{Stage 4: Validated Execution Environments}
For the extrinsic, execution-based evaluation, each issue must have a reproducible environment in which tests actually run. We build a per-issue Docker image and verify that the repository's designated tests execute and that the gold patch is applicable. The instances that pass this validation on our primary compute node form the \textbf{382-issue execution subset} used for the enhancer $\times$ solver matrix. Each such instance carries a buildable image, a recorded test command, and a gold patch.

\subsection{Issue Enhancement Conditions}

We evaluate a no-enhancement \textbf{baseline} against a ladder of enhancers of increasing sophistication, so that scale of machinery is controlled:
\begin{itemize}
\item \textbf{No Enhancement (Baseline):} the original issue is passed directly to the solver. Control condition.
\item \textbf{Zero-Shot (Raw LLM):} a single LLM call restructures the issue without agent-level tool use, measuring the value of prompt-only rewriting.
\item \textbf{Ready-to-use agents:} \textbf{OpenHands}~\cite{wang2024openhands}, \textbf{SWE-agent}~\cite{yang2024swe}, and \textbf{Aider}~\cite{aider2024}, each a $\sim$30-step agent loop given the issue and repository access and instructed to enhance the description. These rewrite \emph{unconditionally}.
\item \textbf{\ourmethod{} (reward-gated):} a managed enhancer that \emph{gates} on a learned reward model and only rewrites reports it judges low-quality, using retrieval-augmented (RAG) grounding. This is a \emph{selective} enhancer (Section~\ref{sec:cl}).
\end{itemize}

\subsection{Solver Agents}

To evaluate enhancement through downstream solving impact, we use three independent solver agents: \textbf{OpenHands}~\cite{wang2024openhands}, \textbf{SWE-agent}~\cite{yang2024swe}, and \textbf{Aider}~\cite{aider2024}, each in solving mode. Using multiple independent solvers reduces the risk that enhancement effects are artifacts of a single solver; an enhancement that helps across solvers provides stronger evidence of genuine quality improvement.

\textbf{Controlled model.} Every enhancer and solver is driven by a single open-weight model, \textbf{Qwen3-32B}, served from a private inference endpoint at temperature 0.0. Holding the model fixed isolates the \emph{enhancement method} as the only variable, so any difference is attributable to the rewriting, not to model capability. Enhancement and solving execute in isolated Docker environments to prevent cross-contamination.

\subsection{Evaluation Framework}
\label{subsec:evaluation}

Our evaluation uses the SWE-bench-Live harness~\cite{zhang2025swebenchlive, jimenez2024swebench} to assess solver-generated patches against ground-truth tests.

\subsubsection{Resolved Rate (P2P)}
We score a patch as \emph{resolved} if, after applying it (plus the issue's test patch) inside the validated image, the repository's designated P2P tests execute and pass with no failures:
\begin{equation}
\text{Resolved} = \begin{cases} 1 & \text{if all P2P tests pass} \wedge |\text{P2P}_{\text{observed}}| > 0 \\ 0 & \text{otherwise} \end{cases}
\end{equation}
We report \textbf{P2P-resolved} rather than the stricter SWE-bench F2P criterion because the offline-derived F2P labels proved unusable at this scale---only 4 of 74 evaluable instances carried a gold-passing F2P label---so requiring them would collapse the sample. P2P-resolved is a no-regression + de-facto-fix signal (the applied test patch supplies the fix-relevant tests); we treat it as directional, and Section~\ref{sec:threats} discusses this threat.

\subsubsection{The Evaluability Gate}
Not every issue can be trusted to evaluate. We gate on a \textbf{gold-patch probe}: an instance is \emph{evaluable} only if the gold patch itself passes under the chosen method. Because a single generic test command fails on many repositories (framework-specific runners, stale node-IDs), we combine three methods per instance and keep whichever the gold patch validates: \textbf{v2}, the repository's real validated test commands recovered from the build; \textbf{v3}, a label-agnostic file-level run (execute the test files, require $\ge 1$ passed and $0$ failed---robust to mislabeled node-IDs); and \textbf{v1}, a generic fallback. This lifted evaluable coverage to \textbf{73.0\% overall (279/382)}---and up to 75.8\% on the largest tranche---versus $\sim$30\% for a single generic method.

\subsubsection{Enhancement Coverage and Delta}
\emph{Coverage} is the proportion of issues an enhancer actually modifies, $\text{Coverage} = |\{i : E(i) \neq i\}| / |I|$. The primary comparison metric is the resolved-count \emph{delta} against the baseline (Eq.~\ref{eq:enhancement_value}); a positive delta indicates net improvement, a negative delta indicates that enhancement \emph{harmed} solving.

\subsubsection{Statistics}
For each enhancer-vs-baseline comparison on a given solver, outcomes are \textbf{paired} (same issues, with vs.\ without enhancement), so we use the \textbf{exact McNemar test} on the discordant pairs and report the pair counts. We report \textbf{Wilson 95\% confidence intervals} on each resolved rate. Effect sizes are absolute differences in resolved count over the fixed evaluable denominator (empty or failed patches count as unresolved).

\subsection{RQ1: What Is the Ability of Generative AI in Enhancing Issue Reports?}

\subsubsection{The correctness matrix --- no enhancer improves any solver}
Table~\ref{tab:matrix} gives the final correctness matrix at $n=382$ (279 gold-evaluable issues), with each enhancer compared to the baseline for each solver. \textbf{Among the three agentic enhancers---the controlled comparison, all built on the same $\sim$30-step agent loop---no enhancer $\times$ solver comparison reaches significance; every $p \ge 0.489$, and the largest absolute effect is 7 issues out of 279.} The one comparison that could be called a ``best case''---Aider-enhancement into the OpenHands solver ($+7$)---is nowhere near significance and is not the pairing any prior signal predicted. The crudest enhancer, a single zero-shot prompt (Raw LLM), does not help either and if anything \emph{hurts}: it leaves OpenHands unchanged ($+1$, $p=1.0$) but lowers Aider by 12 ($-12$, $p=0.213$) and SWE-agent by 6, the latter's nominal $p=0.031$ being a non-determinism artifact on the error-prone SWE-agent solver rather than a real effect (Table~\ref{tab:matrix}, footnote). That the least sophisticated enhancer trends negative, not positive, is consistent with the study's arc: added text perturbs the solver without adding solver-actionable signal.

\subsubsection{The one promising signal was sampling noise}
At $n=100$ the headline pairing (OpenHands-enhancement $\rightarrow$ Aider solver) looked promising: $+4$ resolved (30$\rightarrow$34), $p=0.388$. Replication kills it (Table~\ref{tab:scale}): the effect \textbf{shrank toward zero and the $p$-value rose toward 1} as data accumulated---the diagnostic of a non-effect, not of insufficient power. A genuine effect of fixed size sharpens under more data; this did the opposite. The same pattern held for the OpenHands solver, where an $n=74$ ``$+6$'' reversed to $-3$ on a fresh 100 issues before settling near null. Had we stopped at $n=100$, the paper would have carried a false positive.

\subsubsection{Solver choice dominates; enhancement perturbs without direction}
\label{sec:rq1-solver}
Two robust facts survive at every scale. \textbf{(1) Solver capability is the dominant factor:} baseline resolved rates are Aider 44\% $\gg$ OpenHands 22\% $\gg$ SWE-agent 6\%, stable across all three tranches and far larger than any enhancement effect---the choice of \emph{who fixes} matters an order of magnitude more than \emph{how the report is worded}. \textbf{(2) Enhancement is active but directionless:} for the two responsive solvers, 65--78 issues per comparison change outcome (discordant pairs)---23--28\% of the evaluable set---but the flips are balanced (helps $\approx$ hurts), so there is no net gain. A model-fit note reinforces the point: the SWE-agent solver is effectively inert to enhancement ($0$--$1$ discordant pairs) because, with Qwen3-32B, the large majority of its runs terminate in an agent-protocol error before any patch is produced ($\sim$86\% in a 100-issue audit)---a failure of the model--harness interface, not of the issue text.

\finding{\textbf{RQ1 Summary.} Across the controlled agentic enhancer $\times$ solver matrix on 279 evaluable issues, no enhancer improves fix correctness for any solver (all McNemar $p \ge 0.489$); the crudest zero-shot prompt enhancer only ever matches or hurts. The one small-sample signal regressed toward zero under replication---a non-effect. Solver capability (Aider 44\% $\gg$ OpenHands 22\% $\gg$ SWE-agent 6\%) dominates, and enhancement perturbs a quarter-to-a-third of outcomes without net direction.}

\subsection{RQ2: What Features Are Related to a Better Enhancement?}

\textbf{Approach.} From each issue's title and body we extract the full \textbf{81-feature SE representation} of prior reward-model work---spanning size, readability (Flesch, Flesch--Kincaid, ARI), part-of-speech counts, structural markup (fenced/inline code, URLs, images, checklists, headers, lists, tables), content flags (stack trace, error message, logs, reproduction steps, expected/actual behavior, environment info), and lexical statistics. We use it two ways: \emph{descriptively}, tallying which features an enhancement \emph{adds}; and \emph{predictively}, regressing a success outcome on the features under two operationalizations---an \textbf{extrinsic} label (the enhanced report yields a downstream resolved patch), over the 81 SE features; and an \textbf{intrinsic} label (the learned reward model scores the enhanced report $\ge 0.5$), over the full \textbf{581-feature} set (81 SE $+$ 500 TF-IDF terms). Both use L1-regularized logistic regression tuned by 5-fold cross-validation.

\subsubsection{What enhancement adds}
Comparing SE features before and after enhancement (OpenHands, over its 304 truly-enhanced issues), the additions are a \textbf{uniform template}: the agent rewrites almost every report into a structured Problem / Reproduction / Expected / Actual form (Table~\ref{tab:added}). These are precisely the fields the reward model rewards, which explains the intrinsic gain below; but several---reproduction steps, expected/actual behavior---are facts the agent cannot know and often \emph{invents}, foreshadowing why they do not help the solver.

\subsubsection{No feature predicts a better enhancement}
\textbf{Extrinsic view.} The 81-feature model reaches 5-fold cross-validated ROC-AUC $=0.55$---indistinguishable from the 0.50 no-signal line. L1 retains 14 features with modest odds ratios (Table~\ref{tab:l1}); the strongest are \emph{informativeness} properties of the \emph{original} report (bodies with logs, OR 1.36; a stack trace, OR 1.20), not of the rewrite. On the 65 issues where enhancement \emph{changed} the Aider outcome, it helped 33 and hurt 32; predicting helped-vs-hurt yields ROC-AUC $\approx 0.58$ at $n=65$---no reliable signal.

\textbf{Intrinsic view --- the key contrast.} With the full 581-feature representation and the reward model, enhancement is \emph{not} inert: original score mean $0.473 \rightarrow$ enhanced $0.578$; $218/382$ (57\%) of reports improve and $122$ (32\%) cross from low- to high-quality. Yet \emph{which} issue gets a successful enhancement is still unpredictable from its 581 features (AUC $=0.49$, chance). The agent enhances \textbf{uniformly}---turning almost any report into a similarly structured, higher-scoring one---so no input feature discriminates success. Table~\ref{tab:models} summarizes: all three feature models land at chance.

\subsection{RQ3: How Are Issue Reports Enhanced?}
\emph{(Qualitative analysis in progress; corpus collected.)} We open-code a stratified sample of agent-generated enhancements (across conditions, sampling successes, harms, and no-change cases) for (a) the \textbf{enhancement patterns} applied---restructuring into Problem / Reproduction / Expected sections, appending root-cause hypotheses, extracting stack traces, adding code context---and (b) the \textbf{failure modes}---hallucinated details, over-specification, loss of the original signal, or (for the reward-gated agent) abstention. Two coders label independently; we report inter-rater agreement (Cohen's $\kappa$) and a pattern $\times$ outcome cross-tabulation linking each rewrite move to whether it helped, hurt, or left the fix unchanged. The RQ2 feature-delta analysis (Table~\ref{tab:added}) already indicates the mechanism: the agents apply a \emph{uniform} template that lifts the quality score but, being often unfounded, does not help the solver.

\finding{\textbf{RQ3 Summary (preliminary).} Enhancement is a uniform restructuring into Problem/Reproduction/Expected/Actual sections. Because reproduction and expected/actual fields are frequently invented rather than grounded, they raise intrinsic quality without adding solver-actionable signal---the mechanism behind the directionless perturbation in RQ1.}

\section{Discussion}
\label{sec:discussion}
%==============================================================================

\subsection{Why Enhancement Fails to Transfer}
The issues in an execution-gated repair benchmark are, by construction, \emph{already actionable}---they were selected because a solver could plausibly fix them. Rewriting an already-actionable report adds little signal and can just as easily perturb the solver off a working trajectory as onto one. Enhancement may help most exactly where these benchmarks contain the fewest examples: genuinely underspecified reports. This reframes the ``enhancement paradox''---that adding information does not help---as a selection effect of the benchmark, not a universal law.

\subsection{Measurement Discipline Was Decisive}
Two classes of infrastructure artifact would each have manufactured a false result if left uncorrected, and both were caught by cross-checking rather than trusting raw counts: (i) \textbf{solver timeouts under concurrency}---slow iterative solvers, and even Aider on heavy repositories, hit wall-clock limits and produced empty patches that are \emph{not} real failures; re-solving at lower concurrency recovered them (e.g., 20 of 27 Aider timeouts recovered at a median 881\,s). (ii) \textbf{Permission-lost patches}---the runtime occasionally wrote its patch file unreadable to the host, silently zeroing $\sim$2\% of OpenHands results; these were recovered by a privileged read. A study scoring the raw output would have reported spuriously low---and unevenly distributed---enhancement effects.

\subsection{The \ourmethod{} (Reward-Gated) Arm}
\label{sec:cl}
The agents above rewrite \textbf{unconditionally}. Our managed enhancer, \ourmethod{}, instead \emph{gates} on a learned reward model and only rewrites reports it judges low-quality. Its reward model judged \textbf{216 of 382 issues (57\%) already adequate and abstained} (returning the original), acting on the other \textbf{166 (43\%)} with RAG-grounded rewriting---a \emph{selective} enhancer and a cleaner test of whether \emph{targeted} enhancement transfers. The methodologically correct comparison is on the subset it \emph{chose to rewrite}; on the \textbf{129 evaluable issues \ourmethod{} rewrote, no solver improves} (Table~\ref{tab:cl}). A cautionary note: over \emph{all} 279 evaluable, the SWE-agent comparison reads $\Delta{-}9$, $p=0.004$---\emph{apparently} significant. It is an artifact of non-determinism: 6 of those 9 ``losses'' fall on \emph{abstained} issues whose text was identical to baseline, so they reflect run-to-run solver variance, not any effect of rewriting. The enhanced-only subset removes this confound and shows the true null. The takeaway completes the arc: \textbf{neither unconditional generic enhancement nor selective reward-gated enhancement improves downstream fix correctness.}

\subsection{Cross-model robustness: a frontier solver}
\label{sec:crossmodel}
Our controlled design holds the model fixed at an open-weight Qwen3-32B, which raises the question of whether the null is an artifact of a weak solver. To test this, we re-ran the strongest cell---enhancer Aider into the OpenHands solver---on the 279 evaluable issues with a stronger, function-calling-native commercial model (GPT-5-mini) for \emph{both} the baseline and the enhanced condition (a valid paired comparison, since both share the model). Two things change and one does not (Table~\ref{tab:crossmodel}). The absolute resolve rate rises sharply---OpenHands' baseline goes from \textbf{22\%} (Qwen3-32B) to \textbf{56\%} (GPT-5-mini), a $2.6\times$ increase---confirming that solver/model capability, not report wording, is the dominant lever. But \textbf{enhancement still does not help}: $155 \rightarrow 159$ resolved ($\Delta{+}4$ of 279, McNemar exact $p=0.712$), and the effect remains directionless (66 discordant pairs: 31 hurt, 35 helped). A $2.6\times$ more capable, tool-calling-native solver does not make enhancement transfer to correctness---the negative result is robust across a weak open model and a strong frontier model.

\subsection{Capability spread across many models}
\label{sec:spread}
We broaden the two-model check to the \emph{entire local model inventory} of our server as an illustrative probe---every model available on the shared Ollama endpoint. On a 20-issue sample drawn from the issues GPT-5-mini resolves at baseline---i.e., issues that are \emph{provably solvable}---we run the same enh:Aider $\rightarrow$ sol:OpenHands cell (cap 30) with each model, plus two commercial references (Table~\ref{tab:spread}). Two patterns are stark. First, capability is a \textbf{cliff, not a slope}: GPT-5-mini resolves all 20 (by construction), the strongest open model (Qwen3-32B) resolves only 6, and every other model---open or commercial---resolves 0--4. On issues \emph{known} to be solvable, only the frontier model reliably closes them in the agent loop. Second, consistent with RQ1, \textbf{enhancement helps none of them}: the baseline-to-enhanced change ranges $-4$ to $+2$ across all nineteen models that load (two further server models would not load at all on the available Ollama/driver), uniformly negligible or negative. Notably, code-specialized models (Qwen2.5-Coder, DeepSeek-Coder, Granite-Code) fare no better than general ones---\emph{agentic} competence, not coding knowledge, is the bottleneck.

A trajectory audit of this cell identifies the mechanism behind the cliff, and it is one of \textbf{submission, not fix quality}. GPT-5-mini emits a well-formed patch on 20/20 instances (median 1.2\,KB, touching a single file); every other model emits \emph{no patch at all} on 13--20 of the 20. The models do not lose a code-correctness contest---they never reach the point of proposing a fix, dying in the agent loop either by repeating an identical action (\texttt{AgentStuckInLoopError}; 17/20 for DeepSeek-Coder-v2-16B, 16/20 for Mixtral-8$\times$22B) or by exhausting all 30 iterations without converging (14/20 for Qwen2.5-Coder-32B, 13/20 for GLM-4.7-flash). The failure mode ``clean patch that does not fix the bug'' is essentially absent from the data. Two controls localize the deficit further. It is \emph{not} tool-calling support: GPT-4.1-mini is function-calling-native, like GPT-5-mini, yet still emits 19/20 empty patches and exhausts the iteration cap 10 times. And it is not code specialization: the three code-tuned models emit zero well-formed patches between them. What separates the frontier model is sustained agentic competence---keeping a long multi-step task coherent and terminating deliberately---which also makes it the \emph{fastest} model in the set ($\sim$2\,min median versus 3--25\,min), because it converges rather than thrashes. This is a small, deliberately selection-biased spot-check (20 issues, chosen as GPT-5-mini-solvable, single seed) and \emph{not} a powered comparison; we report it only to show that the RQ1 null and the solver-dominance finding persist across the full capability range of models available to us.

\subsection{Implications for Practice}
For automated repair on already-actionable issues, effort is better spent on the solver and the underlying model than on rewriting the input. Enhancement systems should prioritize verified, factual context injection over generative analysis, and enhancer--solver co-design over generic rewriting. The solving-as-evaluation paradigm gives researchers an objective, reproducible measure of enhancement quality; before deploying enhancement, teams should validate that their specific enhancer--solver combination produces positive deltas on representative, execution-gated data.

%==============================================================================
\section{Threats to Validity}
\label{sec:threats}
%==============================================================================

\textbf{Construct --- the metric is P2P-only.} Our resolved criterion is no-regression on P2P tests, augmented by the applied test patch, not the stricter F2P criterion, which the offline labels could not support at scale (only 4 of 74 evaluable instances carried a gold-passing F2P label). Consequently our result rules out a \emph{large} correctness effect and shows no \emph{directional} one, but cannot certify a strict-fix effect of small magnitude; re-deriving fix-tests from execution is the highest-value follow-up.

A specific consequence deserves emphasis, because it bounds how far the per-model counts in Table~\ref{tab:spread} can be read. Since the criterion requires only that the P2P suite be green, a submission that \emph{fails to apply} leaves the repository untouched, keeps P2P green, and is therefore credited as a solve. Auditing the submissions confirms this occurs: all four of Llama-3.3-70B's baseline solves in Table~\ref{tab:spread} are of this kind---one submission is 60 characters of English prose rather than code, one is a raw Python source file rather than a diff, and two are multi-megabyte \texttt{diff -ruN} dumps in which the entire repository appears as deleted (the agent having destroyed its own workspace). In each case the instance carries no F2P tests and the harness's own report records \texttt{resolved: false}. The effect is confined to the low end of the capability range, where models submit malformed output at all---GPT-5-mini's submissions are uniformly well-formed---but it means the small nonzero counts among weak models should be read as an \emph{upper bound}, and it argues for requiring a non-empty, cleanly-applying patch as a precondition for counting a solve in future work.

\textbf{Internal --- run-to-run solver non-determinism.} Baseline and enhanced conditions are separate stochastic runs, so a fraction of the discordant pairs reflects variance rather than enhancement. This is quantifiable in the \ourmethod{} arm: on abstained (text-identical) issues, 6 of 9 SWE-agent ``losses'' are pure variance, inflating the full-set comparison to a spurious $p=0.004$ that the enhanced-only subset corrects to a null. Because our headline effects are null or small, this variance widens confidence intervals rather than creating a false positive; a definitive study should run multiple seeds per condition.

\textbf{Construct --- \ourmethod{} operates out of distribution.} Its reward model and RAG corpus were trained on an issue-\emph{difficulty} dataset, not repository-repair issues; applying it here is a \emph{transfer} test, and its high abstention (57\%) is partly an out-of-domain artifact.

\textbf{External --- single model, one collection, execution-gated selection.} The controlled matrix uses a single open-weight model (Qwen3-32B). A stronger, function-calling-native model changes absolute rates sharply---our cross-model check (Section~\ref{sec:crossmodel}) shows GPT-5-mini raising the OpenHands baseline from 22\% to 56\%---but \emph{not} the enhancement effect, which remains a directionless null ($\Delta{+}4$, $p=0.712$); we nonetheless cannot rule out a different effect for other model families or agent scaffolds. The 382 issues are, by construction, actionable, so they under-represent the genuinely underspecified reports where enhancement is most plausibly useful. Our dataset is also restricted to popular Python repositories, limiting generalizability.

\textbf{Conclusion --- evaluability coverage.} We score only the 73.0\% (279/382) gold-validated subset; the un-evaluable 27\% are excluded rather than assumed-failed. The multi-method gate is designed to keep that fraction small and repository-diverse.

%==============================================================================
\section{Conclusion}
\label{sec:conclusion}
%==============================================================================

We asked whether improving a bug report's text improves an LLM agent's fix, and answered it extrinsically, at scale, by executing patches against real tests. Across 382 issues, a baseline and enhancers spanning a zero-shot prompt to a reward-gated agent, three solvers, and a fixed model, \textbf{issue enhancement produced no statistically significant improvement in fix correctness} (all McNemar $p \ge 0.489$ at $n=279$ across the controlled agentic enhancers, with a zero-shot prompt enhancer likewise never helping), and the one small-sample signal regressed toward zero under replication. What proved robust is that solver choice governs outcome (Aider 44\% $\gg$ OpenHands 22\% $\gg$ SWE-agent 6\%) and that enhancement perturbs a quarter-to-a-third of outcomes without net direction. The negative result holds for our own selective, reward-gated method as well: on the issues it rewrote it improves no solver, and its most notable behavior is to abstain on the majority of already-actionable reports. No feature predicts a better enhancement, yet enhancement reliably raises the intrinsic quality score---text-quality gains that do not transfer to program repair. We offer this as a rigorous negative result, made trustworthy by a gold-gated, multi-method evaluability protocol (73.0\% coverage) and an artifact-recovery discipline. Whether enhancement helps on genuinely \emph{underspecified} reports, and whether a stronger solver model changes the picture, are the natural next studies. We release the benchmark, evaluation pipeline, and experimental artifacts to support future research.
